# TypeStat WPS 加载项

把 WPS 文字（Writer）里**精确的新增/删除字符数**上报给 TypeStat。

为什么需要它：全局键盘钩子只数得出「按了多少次键」，数不出「打了几个字」。
拼音打一个汉字在钩子看来可能是 5 次按键（逐个敲）也可能是 1 次（整句上屏），
钩子无从区分。只有 WPS 自己知道这次改动往文档里塞进去了几个字符。

**隐私边界**：只上报两个整数（新增几个字、删掉几个字）。
`Range.Text` 只在内存里取一次长度随即丢弃——不存、不传、不落盘。
诊断对话框里显示的也只有长度和事件类型，没有正文。

## 装

在 TypeStat 的「**适配器**」页点「装进 WPS」。加载项文件就编在程序里，它会写到
`%APPDATA%\kingsoft\wps\jsaddons\TypeStat_1.0.0\`，把端口和令牌填进 `js/config.js`，
并在同级的 `publish.xml` 里登记一条。**没有脚本要跑，也不用装 Node**——
改这份源码之后必须重新编译 TypeStat，装出来的才是新的（`include_str!` 是编译期读的）。

（目录约定、`publish.xml` 字段、`<名字>_<版本>` 的命名，都取自 WPS 官方脚手架
`wpsjs` 包的 `src/lib/build.js`，不是猜的。要改这里的机制，先回去核对那个文件。）

手动装，或者装到另一台机器上：同一页的「存出插件文件」会把这份加载项（含本文件）
和 Obsidian 插件一起存到一个文件夹里，照上面那个目录结构复制过去，
再把 `js/config.example.js` 复制成 `js/config.js` 并填上端口和令牌。

**装完必须完全退出 WPS 再打开**——加载项只在 WPS 启动时加载一次。

## 验证

1. 打开一个文档，功能区应该多出「**TypeStat**」选项卡
2. 点「统计状态」，看对话框最上面那条横幅：应该是绿色的「监听中」
3. 在文档里敲几个字，对话框里「收到的 ContentChange 事件」应该开始涨
4. 点「测试连接」——向接收端发一次空上报（不落库），确认端口和令牌都对
5. 回到 TypeStat 的今日看板，WPS 的精确字数应该出现了

## 字符数是怎么计出来的：文档字数的变化量

**不需要任何校准，装完直接用。** 字符数取 `doc.Characters.Count` 的**逐次变化量**：

```
每收到一次 ContentChange：
    读一下这次改完之后文档有多少个字符
    和上一次的差 = 这次改动往文档里净放了几个字
    差是正的 → 记为新增；负的 → 记为删除；0 → 忽略
```

方向也由这个差的正负决定，**压根不需要知道 `WdContentChangeType` 等于几**
（那玩意的数值官方声明文件里没导出，枚举名在 `wpsapiex.dll` 的字符串表里、
数值在 typeinfo 里，按偏移取不到；我按声明顺序猜过两次，第一次猜 1/2、
真机上是 0/1，整体偏了一位）。`changeType` 现在只作为证据记在「最近事件」里。

**为什么这个量法必然对**：逐次变化量求的是望远镜和，
`Σ(后 − 前) = 最后一次字数 − 第一次字数`，**跟中间发生了什么无关**。
输入法组合、粘一整段、WPS 内部把整段重排一遍——无论哪种，总数永远精确等于
文档最终和最初的差。

### 之前的错：把 Range 的长度当成了增量

第一版用的是 `Range.Text.length`（后来又加了 `Range.End − Range.Start` 兜底）。
**真机实测（2026-09-23）证明这两个字段给的都不是增量，而是「这次改动覆盖的那一片
区域有多长」。** 用户敲 4 个汉字，它们报的是 11、13、14、15、16——那是**整段在长**，
每敲一个键涨一点。于是同一分钟记了 109 个字符，而实际按键只有 14 次。
删除那边更彻底：类型 1 的事件 Range 全是空的，全被「长度 0」挡掉，
一天 126 次退格只记到 2 个删除字符。

**而且这两个字段在每一行都相等**（11/11、13/13…），所以原来那套「len 和 span
哪个和字数变化量对得上就用哪个」的判据**从原理上发现不了这个错**。
判据要贴着「我真正需要什么」写——我需要的是字数，就该直接去读字数。

### 兜底路（正常情况下用不到）

万一某个 WPS 版本给不出 `doc.Characters.Count`（连着 `COUNT_FAIL_GIVEUP` 次读不到
就判定走不通），加载项会退回老路：靠**自动校准**反推哪个 `changeType` 是插入
（读字数涨跌，只看方向，按类型累计且从不矛盾），靠 `Range` 量大小。
这条路已经被真机证明比不上主路，只作兜底。对话框里「字符数的量法」那一行会
明说是哪条路——**看到它写着「退回 Range + 自动校准」，数字就不该全信**。

主路一旦建立就不会退回：偶尔一次读不到只跳过那一个事件，不让两种量法混着用
（混用会把两套误差叠起来，而且从最终数字上完全看不出来）。被跳过的事件会在
对话框里单独列一行，丢了多少一眼可见。

### 「单次最大新增 / 删除（个）」是「数字虚高」的哨兵

它是**一次改动里最多计了几个字符**：敲字时应该是 1，上屏一个词 2–4，
粘一段才会很大。**总数虚高时看着甚至更「好看」，但「敲一个字单次最大却是 200」
一眼就是错的**——上面那个 Range 的 bug 就是这么被抓住的。超过 10 会标红。

### 怎么在没有 WPS 的情况下验证

```bash
cd wps-addon
node test/calibration.test.mjs    # 在假 WPS 环境里跑真 reporter.js
node test/check-undefined.mjs     # 找「被调用但从没定义」的函数
```

`js/reporter.js` 是纯 JS，可以用一个假 WPS 环境整份跑起来。假环境的做法是
`vm.createContext` 里塞 `window.Application`（内存版 PluginStorage + 空的 ApiEvent）、
一个**必然成功**的 `XMLHttpRequest`（粘一大段会真的触发上报，让它卡住会把后面的
数字全堵在队列里）、`TYPESTAT_CONFIG`，再手工调一次 `reconnect()` 选主。

**两套场景，分清在看哪一套**：

- **主路（J–M）**：字符数取文档字数变化量。`J` 是最小路径；**`K` 是真机那个 bug 的
  回归测试**（Range 报 11/13/14/15/16、字数一直不动，最后才 +4——必须只记 4）；
  `L` 防「把正常的大改动也压掉」；`M` 防切文档时拿两个文档的字数相减。
- **兜底路（A–I）**：Range + 自动校准。要先用 `forceRangeMode()` 连着喂
  `COUNT_FAIL_GIVEUP` 次「读不到字数」把加载项推过去，否则主路会直接接管。

三个坑写在脚本头部注释里（`writeStatus` 有 500ms 节流、时钟必须可控；
假 `Characters.Count` 必须和喂进去的事件同步变化；主路一旦建立就不会退回）。
改脚本前先看一眼。

`check-undefined.mjs` 是补 `writeTypes` 那个洞时顺手写的：`commitLearning()` 一直在调
一个不存在的函数，因为那条分支从没被执行到，所以既没报错也没人发现。

标 `knownLimit: true` 的场景（目前只有 E）**只打印不计失败**——一个永远红的测试
就不再是信号了。E 记录的是**兜底路上**做不到什么（Range 给不出真实大小）；
主路已经没有这个问题。

### 兜底路上的「人工指定」和它自愈的边界

这一节只有在「字符数的量法」显示为「退回 Range + 自动校准」时才有关。

人工指定**优先于自动校准**（`initLearning` 先查 `typestat_manual`），
但这个优先权**有边界**——优先到它明显解释不了眼前发生的事为止：
连续 `UNKNOWN_STREAK_TO_RELEARN`（3）次「改了文字却认不出类型」的事件之后，
标记会被清掉、自动重新校准（见 `noteUnknownType()`）。

为什么需要这条边界：真机上出过这个。用户点了「翻转增删映射」，而翻转只是把两个
列表对调——对调前的列表本身可能缺项。当时打字是类型 0、删除是类型 1，
翻转得到 `插入=[2] / 删除=[1]`：**删除对上了、打字仍然谁也不认识**，
而翻转打上的 `typestat_manual` 又让自动校准跳过，于是这个只覆盖一半的映射被永久冻结。
症状是「删除计上了、打字全漏」，看起来像 WPS 只发删除事件。

想手动回到自动：点对话框里的「**恢复自动校准**」——它清掉 `manual` 和 `learned`
两个标记，并留一个 `typestat_recalibrate` 请求由入口页消费（两个网页文档内存不共享，
只能这样传话）。**注意**：功能区的「**重连监听**」也会把量法状态一起归零重来，
因为那个按钮的含义就是「推倒重来」。

## 出问题时看哪里

| 现象 | 原因 |
|---|---|
| 功能区没有「TypeStat」选项卡 | JS 加载项框架没启用。见下 |
| 横幅说「还没收到加载项的任何状态」 | 加载项没被加载，或 `reporter.js` 没执行到 |
| 横幅红色，说「监听没挂上」 | `window.Application` 还没就绪。点功能区「重连监听」 |
| 「字符数的量法」写着「读不到文档字数，退回 Range + 自动校准」 | 兜底路，数字不该全信。见下 |
| 事件在涨但「计入字符数」一直是 0，横幅说「正在自动校准」 | 只在兜底路上会这样，正常，校准中不计字数。打两个字再按两次退格 |
| 事件在涨、「计入字符数」是 0，且横幅说「自动校准失败」 | 只在兜底路上会这样：`changeType` 的实际取值不在已知列表里。把「最近事件」里的原始类型值填进 `js/config.js`，或用「翻转增删映射」人工指定 |
| 打字计上了，但删除计成新增（或反之） | 只在兜底路上会这样（校准学反了）。点「恢复自动校准」重学，或用「翻转增删映射」 |
| **删除计上了、打字全漏** | 只在兜底路上会这样：映射只覆盖了一半（多半是点过「翻转增删映射」）。再打几个字会自动重学 |
| 字数明显偏大 | 先看「单次最大新增 / 删除（个）」：敲字时它应该是 1。涨到几十上百就是读错了范围。见下 |
| 「其中计上的事件」涨得跟拼音按键一样快 | 那一行是**事件条数**不是字数（单位现在标出来了）。真正的字数是下面「已上报新增字符数（个）」 |
| 测试连接报「令牌不对」 | TypeStat 里重新生成过令牌。在「适配器」页点一次「重新装一次」，再重启 WPS |
| 测试连接报「连不上」 | TypeStat 没在跑，或端口不是 42180 |

### 「长度」和「跨度」现在只是证据

「最近事件」里那两列：**长度**是 `Range.Text.length`，**跨度**是 `Range.End − Range.Start`。
**它们不参与计数**——主路计数用的是「字数」那一列。

留着它们是因为它们是「Range 给的到底是什么」唯一的直接证据，而正是这两列
（每一行都相等、而且一直在随段落变长）暴露出「Range 不是增量」这个 bug 的。
如果跨度那列出现红色的「≠」，说明 WPS 给的 Range 和它附带的内容对不上，
值得记一笔——但**别再拿它们当增量用了**。

### 已经记进库里的错数字怎么办

改量法之前记进去的 WPS 字符数（`char_input`）是虚高的（今天那批 2248 个，
实际按键只有 2739 次），因为它们来自那个把整段长度当增量的量法。
**这些历史数字不会自动修正**——库里存的是一分钟的聚合值，没法回头拆开。
要么留着（知道那几天不可信），要么手工清掉那几行。

### 「条」和「个」不是一回事（这张表最容易读错的地方）

对话框里上半部分**全是「事件条数」，下半部分才是「字符个数」**。单位现在都写在
行标题里了（条 / 个），但之前没写，真机上就出过误会：用户看到「其中计入字符数」
涨得跟拼音按键一样快，以为字数统计是按拼音算的。其实那一行是**事件条数**——
输入法上屏时一次改动可能触发多条 `ContentChange`，条数和字数本来就不成比例。

排查「数字对不对」只看这几行：

| 行 | 正常的样子 |
|---|---|
| 收到的 ContentChange 事件（条） | 打字时在涨；上屏一个词可能涨好几条 |
| 其中计上的事件（条） | 略少于上一行（差的是「未知类型」和「字数没变」的） |
| 单次最大新增 / 删除（个） | **敲字时应该是 1**；上屏一个词 2–4；粘一段才会很大 |
| 已上报新增字符数（个） | 这才是最终进统计库的字数 |

**「单次最大新增」是看穿「数字虚高」最直接的指标**：它记录一次改动里最多计了
几个字符。如果每敲一个字这个数都在涨、涨到几十上百，说明拿到的不是「这次改了
多少」，而是整段甚至整篇——那时上面那个总数看着正常（甚至很好看）也是错的。
超过 `MAX_SANE_ONE_SHOT`（10）会在对话框里标红。这条哨兵是补 `test/` 里场景 E
那个已知限制时顺手加的：E 那种情况（`End/Start` 也取不到、只剩偏大的 `Text`）
方向学得对、大小会偏大，总数上看不出来，但单次最大值一眼就能看见。

顺带一提：输入法（拼音）上屏时 WPS 会把整段中文一次性提交，所以「收到的
ContentChange 事件」通常会少于敲键次数，而「已上报新增字符」会多于事件数——
这是正常的。**但如果「单次最大新增」也跟着变得很大，那就不是输入法，是读错了范围。**

### 功能区没有 TypeStat 选项卡

说明 JS 加载项框架没被启用。这需要在 WPS 安装目录的
`office6\cfgs\oem.ini` 里加 `JsApiPlugin=true`——**这是唯一一处需要动
WPS 安装目录的操作**，而且那个文件是签名过的 OEM 配置，改写有风险。
先确认之后再动，动之前先备份。

## 架构上的四个坑（改代码前先读）

**1. 重连必须能幂等。** 加载项页面被 WPS 重新加载后，旧的 `ContentChange`
注册可能还挂在 `ApiEvent` 上。所以注册时用的是**函数名**而不是函数对象，
并且一律「先 `RemoveApiEventListener` 再 `AddApiEventListener`」——
直接再 Add 一次会让同一次改动被上报两遍，字数凭空翻倍，而且很难发现。

**2. 同一时刻只能有一个实例在收事件。** WPS 到底创建几个加载项页面没有文档
写清楚（可能每个文档窗口一个）。每个页面都注册一遍的话，同一次改动会被上报
N 遍。所以用 `PluginStorage` 里的一份心跳做**单写者选举**：谁的心跳最新谁负责
收事件，其他人让位；心跳过期（页面被关掉）后别人接管，不会留下统计空窗。
只有当选的那个实例会写状态快照，否则诊断对话框会随机读到一份全零的计数。

选举的代码在 `js/reporter.js` 的 `tick()` 里，改之前先看懂让位规则。

**3. 不要猜 WPS 的枚举值，也不要对 Range 的字段提额外要求。** 两条都踩过：

- `WdContentChangeType` 的数值在官方声明文件里没有，在 `wpsapiex.dll` 里也取不到
  （枚举名在字符串表里，数值在 typeinfo 里，按偏移取不出来）。第一版按声明顺序猜了
  `插入=1 / 删除=2`，真机上是 `0/1`——**整体偏了一位**，于是打字落进「未知类型」
  被忽略、删除反被当成插入计上。症状是「事件在涨、字数不动」，看起来像监听没挂上。
- 注意 `0` 是**假值**：任何 `if (changeType)` 之类的真值判断都会把插入当成「没给类型」。
  判定一律走 `inList()` 的严格相等。真机那组 `0/1` 已经固化进
  `test/calibration.test.mjs` 的 F/G 两个用例——这类 bug 症状是「打字全不计、删除正常」，
  最容易复发。
- 第二版改成从字数涨跌自学，但多加了「字数变化量必须正好等于 `Range.Text.length`」
  这道门，真机上 12 个事件一次都没匹配上。**判据要贴着「我真正需要什么」写**：
  我需要的是方向，方向从涨跌就能拿到，长度对不上只是说明别用那个字段。

**4. 改了调用就要确认被调的函数存在。** `commitLearning()` 里调了 `writeTypes()`，
而这个函数**从来没定义过**——一直是 `ReferenceError`。它没暴露，是因为在修好校准之前
`commitLearning` 一次都没被执行到。「新写的分支第一次跑通」和「那个分支第一次被执行」
是两件事，前者会以为后者已经验过了。上面「怎么在没有 WPS 的情况下验证校准逻辑」
那一节就是为了让这种分支能被真的执行一次。
